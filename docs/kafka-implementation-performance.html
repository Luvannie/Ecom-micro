2. Order Service Producer

Order-service phát events với synchronous send (đợi Kafka ack trước khi trả response cho user). Đây là trade-off giữa consistency (đảm bảo event đã được publish) và latency.

2.1 OrderEventProducer

@Component
public class OrderEventProducer {
    private final KafkaTemplate kafkaTemplate;

    public void publishReservationRequested(OrderResponse order) {
        var event = new ReservationRequestEvent(order.id(), order.items().stream()
                .map(item -> new ReservationItemEvent(item.productId(), item.quantity()))
                .toList());
        try {
            kafkaTemplate.send(OrderTopics.INVENTORY_RESERVATION_REQUESTED,
                    order.id().toString(), event)
                    .get(5, TimeUnit.SECONDS);  // synchronous wait
        } catch (Exception e) {
            throw new RuntimeException("Failed to publish for order " + order.id(), e);
        }
    }
}
📦 Topics: inventory.reservation-requested, inventory.reserved, inventory.reservation-failed, order.confirmed, order.cancelled
⚠️ Synchronous Send: .get(5, TimeUnit.SECONDS) chặn thread trong tối đa 5s. Nếu Kafka down hoặc chậm, user request cũng chậm theo. Trade-off đổi lấy strong consistency guarantee.

3. Payment Service — Outbox Pattern

Payment-service dùng Outbox Pattern để đảm bảo event được publish exactly-once ngay cả khi Kafka down lúc commit DB. Events được ghi vào DB trong cùng transaction với business state, sau đó một scheduler publish lên Kafka.

3.1 OutboxPublisher

@Component
public class OutboxPublisher {
    private static final int BATCH_SIZE = 100;

    @Scheduled(fixedDelayString = "${payment.outbox.publish-fixed-delay-ms:5000}")
    public void publishPending() {
        for (UUID id : lockAndCollectIds()) {
            publishOne(id);
        }
    }

    @Transactional
    protected List<UUID> lockAndCollectIds() {
        // SKIP LOCKED để nhiều publisher instances không collide
        return repository.lockTopPending(OutboxStatus.PENDING, PageRequest.of(0, BATCH_SIZE))
                .stream()
                .map(OutboxEvent::getId)
                .toList();
    }

    private void publishOne(UUID eventId) {
        var future = kafkaTemplate.send(event.getEventType(),
                event.getAggregateId().toString(), event.getPayload());
        future.whenComplete((result, ex) ->
            updateStatus(eventId, ex == null ? OutboxStatus.PUBLISHED : OutboxStatus.FAILED)
        );
    }
}
✅ Ưu điểm:
  • No dual-write problem: Event và business state cùng commit trong 1 transaction DB
  • At-least-once: Consumer phải idempotent (check orderId đã xử lý chưa)
  • Horizontal scale: SKIP LOCKED cho phép nhiều payment-service instances cùng publish
  • Buffering: Khi Kafka down, events accumulate trong DB, không mất

4. Consumer Pattern với Resilience

Consumers được wrap trong KafkaListenerResilienceWrapper để áp dụng Resilience4j TimeLimiter và fail-fast nếu handler quá lâu.

4.1 KafkaListenerResilienceWrapper

@Component
public class KafkaListenerResilienceWrapper {
    private final TimeLimiter timeLimiter;

    public KafkaListenerResilienceWrapper() {
        this(TimeLimiterConfig.custom()
                .timeoutDuration(Duration.ofSeconds(5))
                .cancelRunningFuture(true)
                .build());
    }

    public <T> T execute(Callable<T> handler, Consumer<Throwable> onTimeout) {
        var decorated = Decorators
            .ofCompletionStage(supplier)
            .withTimeLimiter(timeLimiter, scheduler)
            .withFallback(java.util.List.of(TimeoutException.class),
                e -> {
                    onTimeout.accept(e);
                    throw new AmqpRejectAndDontRequeueException(
                        "kafka handler timeout (5s) — will be retried by KafkaErrorHandler", e);
                })
            .decorate();
        return decorated.get().toCompletableFuture().join();
    }
}

4.2 Example Consumer

@KafkaListener(topics = OrderTopics.PAYMENT_SUCCEEDED,
               groupId = "order-service")
public void onPaymentSucceeded(PaymentSucceededEvent event) {
    resilienceWrapper.execute(() -> {
        log.info("Processing PAYMENT_SUCCEEDED for orderId={}", event.orderId());
        orderService.confirmOrder(event.orderId());
        log.info("Successfully processed PAYMENT_SUCCEEDED for orderId={}", event.orderId());
        return null;
    }, ex -> log.error("Timeout handling PAYMENT_SUCCEEDED for {}", event.orderId()));
}

8. Trước & Sau khi có Kafka

🔴 Trước khi có Kafka

  • REST chain đồng bộ: order → inventory → payment
  • Một service chết = cả chain chết
  • Tight coupling, không replay được
  • Database lock cascade khi concurrent orders
  • Notification sync, block user response

🟢 Sau khi có Kafka

  • Order chỉ publish event, return ngay (~15ms)
  • Mỗi service consume độc lập, scale riêng
  • Kafka buffer khi downstream chậm/down
  • Event replay từ retention (debug, audit, replay)
  • Notification async, user không phải đợi

9. Trade-offs & Lưu ý

Aspect Pre-Kafka (sync REST) Post-Kafka (async event)
Latency Cao (chain × services) Thấp cho user (chỉ publish)
Consistency Strong (transaction chain) Eventual (consumers apply async)
Failure handling 5xx nếu 1 service down Events queued, retry khi service up
Idempotency Không cần (single-call) Cần thiết (at-least-once delivery)
Observability Tracing qua HTTP chain Tracing phải cover Kafka offsets
Operational cost Chỉ cần services Cần Kafka cluster, monitoring offsets
⚠️ Eventual consistency: Sau khi user POST order, response trả 200 OK với status PENDING. Phải đợi consumers (inventory, payment) apply mới có status CONFIRMED. UI cần polling hoặc websocket để update real-time.
💡 Tip: Nếu cần strong consistency cho critical path (vd payment), dùng Outbox Pattern + idempotent consumer thay vì publish-then-return.

10. Cách chạy benchmark

# Verify Kafka đang chạy
docker exec be-kafka-1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list

# Create benchmark topic
docker exec be-kafka-1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic bench-throughput \
  --partitions 3 --replication-factor 1

# Produce messages + measure throughput
docker exec be-kafka-1 /opt/kafka/bin/kafka-producer-perf-test.sh \
  --topic bench-throughput \
  --num-records 100000 \
  --record-size 1024 \
  --throughput -1 \
  --producer-props bootstrap.servers=localhost:9092

# Consume + measure end-to-end latency
docker exec be-kafka-1 /opt/kafka/bin/kafka-consumer-perf-test.sh \
  --topic bench-throughput \
  --messages 100000 \
  --broker-list localhost:9092
