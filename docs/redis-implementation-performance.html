2. Implementation trong cart-service

Cart-service sử dụng Redis như primary storage thay vì database SQL. Mỗi cart được lưu dưới dạng JSON string với key cart:{userId}.

2.1 CartRepository - Lưu trữ chính

@Repository
public class CartRepository {
    private static final Duration TTL = Duration.ofDays(30);
    private static final Duration LOCK_TIMEOUT = Duration.ofSeconds(5);

    private final StringRedisTemplate redisTemplate;
    private final ObjectMapper objectMapper;

    public Optional<Cart> findByUserId(UUID userId) {
        String value = redisTemplate.opsForValue().get(key(userId));
        if (value == null) return Optional.empty();
        return Optional.of(objectMapper.readValue(value, Cart.class));
    }

    public Cart save(Cart cart) {
        cart.setVersion(cart.getVersion() + 1);
        String jsonValue = objectMapper.writeValueAsString(cart);
        redisTemplate.opsForValue().set(key(cart.getUserId()), jsonValue, TTL);
        return cart;
    }

    private String key(UUID userId) {
        return "cart:" + userId;
    }
}

2.2 Distributed Lock với SETNX

Khi findByUserIdOrCreate được gọi, cần tránh race condition khi 2 request đồng thời tạo cart mới:

public Cart findByUserIdOrCreate(UUID userId) {
    String lockKey = "lock:" + key(userId);
    String cartKey = key(userId);

    // SETNX với TTL = 5s (auto-release nếu service crash)
    Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, "locked", LOCK_TIMEOUT);

    if (Boolean.TRUE.equals(acquired)) {
        try {
            // Double-check inside lock
            String existing = redisTemplate.opsForValue().get(cartKey);
            if (existing != null) {
                return objectMapper.readValue(existing, Cart.class);
            }
            Cart newCart = new Cart(userId);
            save(newCart);
            return newCart;
        } finally {
            redisTemplate.delete(lockKey);
        }
    } else {
        // Retry sau khi đợi lock holder
        Thread.sleep(50);
        return findByUserIdOrCreate(userId);
    }
}

2.3 Optimistic Locking qua Lua Script

Để tránh lost update khi 2 client cùng sửa 1 cart, dùng Lua script chạy atomic trên server:

-- SET_IF_SAME_SCRIPT (atomic)
local key = KEYS[1]
local expectedVersion = ARGV[1]
local newValue = ARGV[2]
local ttl = ARGV[3]

local current = redis.call('GET', key)
if current then
    local currentObj = cjson.decode(current)
    local currentVersion = currentObj.version or 0
    if currentVersion ~= tonumber(expectedVersion) then
        return 'VERSION_MISMATCH'
    end
end

redis.call('SETEX', key, ttl, newValue)
return 'OK'
✅ Ưu điểm: Toàn bộ thao tác (đọc → check version → ghi) chạy trong 1 lần gọi Redis, không có race window — đảm bảo tính nhất quán ngay cả khi có concurrent updates.

3. Implementation trong product-service

Product-service dùng Spring Cache abstraction, ánh xạ trực tiếp lên Redis.

3.1 Cấu hình

  cache:
    type: redis

3.2 Cache Annotations

@Service
@Transactional
public class ProductCatalogService {

    @CacheEvict(cacheNames = {"product-detail", "product-search"}, allEntries = true)
    public Product createProduct(CreateProductRequest request) { ... }

    @CacheEvict(cacheNames = {"product-detail", "product-search"}, allEntries = true)
    public Product updateProduct(UUID productId, UpdateProductRequest request) { ... }

    @Cacheable(cacheNames = "product-search",
               key = "#p0.toCacheKey() + ':' + #p1.pageNumber + ':' + #p1.pageSize")
    public Page<Product> search(ProductSearchCriteria criteria, Pageable pageable) {
        return productRepository.findAll(specification(criteria), pageable);
    }

    @Cacheable(cacheNames = "product-detail", key = "#p0")
    public Product getProduct(UUID productId) {
        return productRepository.findByIdAndActiveTrue(productId)
                .orElseThrow(() -> new ProductNotFoundException(productId));
    }
}
⚠️ Cache Invalidation: Mọi thao tác ghi (create/update/change status) đều @CacheEvict cả 2 cache. Đây là chiến lược cache-aside đơn giản, chấp nhận một số cache miss sau khi write.

6. Trước & Sau khi có Redis

🔴 Trước khi có Redis

  • Cart được lưu trong bảng SQL riêng (cart, cart_item)
  • Mỗi lần findByUserId đều truy vấn DB
  • Concurrency: dùng SELECT FOR UPDATE → blocking
  • Search product: LIKE '%keyword%' quét toàn bộ bảng
  • P95 latency cao, đặc biệt dưới tải nặng
  • DB connection pool dễ cạn kiệt khi concurrent writes

🟢 Sau khi có Redis

  • Cart là JSON string trong Redis, TTL 30 ngày
  • Cache hit: GET đơn giản, ~1-3ms
  • Concurrency: SETNX distributed lock + Lua atomic
  • Search: cache theo (keyword + pageNumber + pageSize)
  • P95 giảm mạnh, throughput tăng 3-5×
  • DB chỉ chịu tải cho writes/admin, không phải reads

7. Trade-offs & Lưu ý

Aspect Trước (DB only) Sau (Redis)
Durability ✅ ACID guaranteed ⚠️ Cache có thể mất → cần rebuild từ DB hoặc chấp nhận TTL
Memory cost Rẻ (disk-based) Đắt hơn (RAM) — cần estimate: ~1KB × số carts
Consistency Strong consistency Eventual — @CacheEvict xử lý invalidation
Read latency 10-50ms 1-5ms (in-memory)
Write latency 20-60ms 5-25ms (atomic Lua)
Horizontal scale Khó (cần session affinity) Dễ (Redis chia sẻ giữa instances)
⚠️ Cache Stampede: Khi key expire, nhiều request đồng thời có thể tạo "thundering herd" lên DB. Cart-service giảm thiểu bằng SETNX lock trước khi recompute.
